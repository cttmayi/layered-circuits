# 拆分设计：元件 → 门 → 模块

> 目标：把玩法拆成三层，**契约（协约）只钉在最底下的元件层**，让玩家从某一章起
> 完全不用再碰元件，直接用「门」搭复杂模块 —— 计算因此变简单。

## 0. 三层阶梯

```
第 0 层  元件 ──► 基础门       ← 只有这一层受契约约束（元件集 / 成本线 / 延迟线）
第 1 层  门   ──► 组合模块     ← 与契约无关：门已经把契约"吃"进去了（契约在门的内部）
第 2 层  模块 ──► 整机         ← 与契约无关
```

一句话原则：**契约约束的是"用哪些元件、元件多贵多慢"，不是"怎么搭电路"。**
门一旦封装好，它的成本和延迟就把契约的差异吸收掉了，上层不必再关心。

## 2. 顶层菜单：按"层"分章

| 章 | 玩家用什么 | 关卡字段 | 契约菜单 |
|---|---|---|---|
| 第 0 章 · 元件与门 | 只给元件，手搭门 | `moduleAccess: 'none'` | **显示**（可换 rtl / cmos / ttl / dtl） |
| 第 1 章 · 用门搭模块 | 给一组基础门 | `moduleAccess: 'listed'` + `allowedModules` | 隐藏 |
| 第 2 章 · 用模块搭整机 | 给自己的模块（封装玩法） | `moduleAccess: 'all'` | 隐藏 |
| 第 3 章 · 时序 | 同上 + 时钟关 | 同现状 | 隐藏 |

每章开头一句"本章只用什么"，把"契约只作用在元件层"讲成世界观，而不是藏在代码里。

## 3. 关卡内的菜单：左侧面板三个区（第一步要做的改动）

```
┌ 我的元件    可用 2/6        ← ① 受契约约束（复杂关默认收起）
│   三极管 NPN   价格 2
│   基极高电平导通 ···  延迟 1.0 ns
├ 基础门      本关 3 个       ← ② 新建：本关提供的门（teachingModulesFor）
│   与非门       成本 10
│   2 入 / 1 出 ·····  延迟 2.5 ns
├ 我的模块    12 个           ← ③ 现状：自己封装的
│   半加器       成本 60
│   1 入 / 1 出 ·····  延迟 6.5 ns
```

- ① **我的元件**：只有这一区受契约约束。复杂关整区收起 —— 从第 1 章起玩家根本不用看元件。
- ② **基础门**：新增区，内容 = 本关允许的门（`allowedModules` 过滤后的
  `teachingModulesFor(family)`），卡片复用现有模块卡样式（成本 + 延迟 + 入/出），
  拖放或"点击选中 → 点画布"都可用。逻辑版口径下不显示延迟（沿用现有 `mode` 开关）。
- ③ **我的模块**：不变。
- **默认展开策略**：关卡声明默认展开哪一区（如 `openSections: ['gates']`），
  第 1 章进来只展开②、①收起。`useOpenSections` 已存在，加默认值即可。
- **契约菜单**（`FamilyPicker`）：只在第 0 章出现，其余章节隐藏。

## 4. 连带的数值改动（不能漏）

允许用门之后，参考解会比手搭更省 —— 现有的 `budgetHalf` / `optimalHalf` / 延迟预算必须
按**门版参考解**重标，否则成本线和延迟线会失真。

- 参考解：`teachingSolutionOf(levelId, family)` 已支持按契约出解，再加"门版参考解"。
- 成本线 = 门版参考解成本 ×2（沿用现有口径）；延迟预算 = 门版参考解实测延迟 ×2
  （沿用现有口径，见 `levels-ari.ts` 里 52 ns / 76 ns 两处的做法）。
- **门要收钱**（= 其内部元件成本，例如非门 6 元）。不收钱则"成本最优"这条核心玩法失效。
- **判定器零改动**：模块是编译期内联的，成本/延迟照算；逻辑版 / 时序版开关同样适用。

## 5. 一期最小可玩（实施顺序）

1. **菜单分区**：①元件 ②基础门 ③我的模块 + 分区默认展开策略。
2. **注入门**：关卡 `moduleAccess !== 'none'` 时把本关允许的门注入画布库。
3. **一关示范**：「用门搭半加器」（`moduleAccess: 'listed'`，参考解只用门）。
4. **重标该关成本线 + 延迟预算**（先量后改）。
5. 通了再铺第 1 章（8–10 关）与其余章节。

## 6. 已拍定的三个选择

1. **第 1 章先给三个门**：非门 + 与非门 + 或非门；其余门（与门 / 或门 / 异或门）按关卡逐步给。
2. **第 0 章（手搭门）只留 3 关**：非门 / 与非门 / 或非门各一关，别让玩家手搭十个门。
3. **门允许展开内部电路**（双击模块已有的能力）：保留"门是元件搭的"这层可见性，
   避免门变成黑箱。

## 9. 逻辑版新引擎：门级求值（7 个门是原子，去掉强弱）

### 9.1 为什么

逻辑版（第 8 关起 20 关的判定口径）此前只是**抹平延迟**，底下仍然把画布上的门展开成
NPN / RES / DIO 求值，而且带着强/弱驱动那一套（强压弱、同强度冲突判 X）。它算的是"真实电路的
电气行为"，在逻辑版里是多余复杂度：`s3-calc` 展开后有 **6191 个元件**，逻辑版判定也要 1.9 s，
手机更扛不住。

### 9.2 模型

- **7 个基础门是原子**（非/与非/或非/与/或/异或/同或）：直接按真值函数算，**不往下钻到元件**。
- **复合模块 = 门之间的连线**（全加器、BCD→二进制…都只是门的组合）。
- **值域 4 个：0 / 1 / X / Z**（Z = 悬空）。**没有强度、没有优先级**：
  同节点多驱动 0 撞 1 → X；无驱动 → Z；不比"谁更强"。
- **Kleene 三值逻辑**：AND 遇 0 即 0（另一输入 X 不影响）、OR 遇 1 即 1。
  这与时序版电路稳定后的结论一致，也是"逻辑版只判逻辑"该有的口径。
- **时序器件**（D 锁存 / DFF / 寄存器）在无延迟下是**代数环**（交叉耦合门），
  必须由调用方用「**状态 + 时钟沿**」模型处理：当前值保持，时钟沿更新。这一层不在门级核心内。
- **适用边界**：只对**纯模块**的设计启用（第 8 关起的 20 关正好全是）；
  自由模式里元件与模块混搭的设计**维持现状**（走元件级逻辑求值），风险最小。
  1~7 关是时序关，逻辑版本就不在那几关生效，元件级语义在时序版里完整保留。

### 9.3 落地进度

- ✅ **第 1 步（已完成）**：`packages/sim-core/src/gate-logic.ts` —— 4 值核心 +
  7 门真值函数 + `mergeDrivers`（多驱动合并，无强弱）+ 多输入折叠 + 输入不足按 X 补齐。
  10 条测试：真值表、Kleene 吸收律、Z→X、多输入、多驱动、4×4 全枚举。
- ⬜ **第 2 步**：按 `Design.nets` 把门连起来求值（拓扑排序 + 迭代到稳定）。
- ⬜ **第 3 步**：时序器件的状态 + 时钟沿模型（锁存器 / DFF / 寄存器）。
- ⬜ **第 4 步**：判定与画布仿真接上这条快路（纯模块设计自动启用，混搭不变）。
- ⬜ **第 5 步**：逻辑版下模块展开只到门（看不到元件层）。
- ⬜ **第 6 步**：实测 speedup（`s3-calc` 判定 21.9 s → 目标毫秒级）+ 守住

## 10. s3-calc 门级/元件级分歧排查记录（2026-10）

目标：让 `s3-calc` 在对照表仪器（`apps/studio/test/gate-fast-report.test.ts`）里变成
「差异 0/N ✅」，通过后才允许进 `GATE_FAST_LEVELS` 白名单。

### 10.1 修好了一个真 bug：一个引脚接多条网名（pin → net 索引只认一条）

**症状**：门级读数与元件级**整片相反**（元件级上电 Q=1，门级读成 0）。

**根因**：`packages/sim-core/src/gate-netlist.ts` 的 `makePinIndex` 原来用
`Map<pinKey, netId>` —— 一个引脚只记住**最后一条** net。但门版参考解里
**同一个引脚挂多条不同网名**是常态，而元件级编译（`flatten.ts`）会把同一引脚上的
各条网名**并成同一个节点**（电气上就是一根线）。于是只有"最后一条 net"拿到驱动，
别的网名永远停在 0：

- 八位寄存器 `q0..q7` ↔ 顶层 `acc0..acc7`（`mod8.q[i]` 同时挂在两条网上）；
- 数字输入寄存器 `q0..q7` ↔ `er0..er7`；
- ALU 的异或/全加器各段、`sumc*` 进位链同理。

最小复现（已写成回归测试 `packages/sim-core/test/gate-pin-alias.test.ts`）：
一条 net 接在 A 门输出上，**同一个引脚**还挂着另一条 net `mid`；修之前 `mid` 永远是 0。

**修复**：`GatePinIndex` 增加 `netsPinTo: Map<pinKey, string[]>`（一个引脚 → 所有 net），
`pinToNet` 保留为首条（兼容旧读法）；驱动推送（`gate-netlist.ts` 与 `gate-seq.ts` 的
3 处 push 循环）改成**写给每条 net**，`readBit` 对多条 net 取 `mergeDrivers` 合并。

**实测（口径要看清：见下）**：这条修复让门级读数不再"整片相反"，
但**没有**让 s3-calc 转绿 —— 门级仍然算不出这一关。见 10.2。

### 10.2 仍未转绿：门级 67 行里 **29 行是"上一次的旧值"**（门级 pass=false）

仪器（`apps/studio/test/gate-fast-report.test.ts`，快路真正生效的口径 `mode:'logic'`）
三轮实测**稳定复现**：

```
s3-calc: 元件级 pass=true 87ms / 门级 pass=false 553ms / 差异 58/67 ❌    完全一致：18/19
```

逐行三方对照（`元件级 / 门级 / 关卡期望`，全 67 行都量过）：

| 行 | 期望 | 元件级 | 门级 |
| --- | --- | --- | --- |
| 1（按 C 清屏） | `3f,3f` | `3f,3f` ✅ | `6f,6f` ❌ |
| 7 | `06,5b` | `06,5b` ✅ | `6f,6f` ❌ |
| 9 | `3f,6d` | `3f,6d` ✅ | `5b,6d` ❌（左位滞后） |
| 45 | `79,79` | `79,79` ✅ | `79,79` ✅ |
| 65（先清屏） | `06,6d` | `06,6d` ✅ | `6f,6f` ❌ |

- **元件级 67 行全对**（`pass=true`）；**门级 38 行对、29 行错**，
  错的那 29 行呈现同一个形态：**读数是"上一拍/上几拍的旧值"**（左位 `disp_t` 明显滞后，
  `disp_u` 常常还是对的）。所以它不是"完全没算"，而是**慢了一拍**。
- 门级耗时不比元件级小（553ms vs 87ms，慢 6 倍）—— 就算修对了，这一关也换不到"快"。

**直接原因（实测，2026-10-06 查清；先前一版说法被仪器假象误导，已更正）**：
**这一关的时钟是"延迟链构成的环形振荡器"，而门级是零延迟求值 —— 振荡被塌成静态电平。**

1. **门级这边**：逐向量量 `settleGateSteps` 的返回，**每个向量都是 `unstable=false`**
   （组合阶段都收敛了，**不存在**"64 轮不收敛"），而 `accClk` 的稳定值是**静态的 0 或 1**。
   寄存器（八位寄存器内部是主从锁存器）要么一直保持（clk 停在 1）、要么一直透明（clk 停在 0），
   两者都不是设计意图 → 29 行读到旧值/错值。
   > 更正：上一版文档写的"64 轮内始终 settled=false、accClk 反复横跳"是**仪器假象**——
   > 探针打在了 `settled = !changed` **赋值之前**，于是一直打印上一次的值。
   > 用赋值之后的打印重测：顶层在 ~10 轮内收敛，`unstable=false`。
2. **元件级这边**（同一份设计、时序口径，`Simulator(trace:true)` 实测 `accClk` 这条 net）：
   上电窗口里它**跳变 12 次**（`500ps=1 1000ps=0 1500ps=1 … 5500ps=1 17500ps=0`），
   按 C 清屏再补一个沿（`112400ps=1`）。**寄存器就是靠这些沿写入的** ——
   这也解释了关卡按键向量为什么都带 `settlePs: 1_000_000`（要留时间给振荡器振几下）。
3. 所以这不是接线/引脚 bug，而是**建模缺口**：零延迟模型里"环路代数收敛 ⇒ 没有沿"，
   而真实电路里延迟链让它一直在振。要放行就得给门级**有界延迟 / 事件驱动推进**（见 10.4）。

**可执行凭据**（这两条测试就是把上面的结论跑出来，且以后会替我们盯住）：
- `apps/studio/test/gate-calc-delay-clock.test.ts`：断言"元件级上电窗口 accClk 跳变 >6 次且 0/1 都出现"
  + "按 C 后还有新沿" + "门级 pass=false、29 行不对"。**哪天门级加了延迟模型，这条会失败**
  —— 那正是回来改本节、并考虑放行的信号。
- `packages/sim-core/test/gate-net-boundary.test.ts`：钉住"顶层 net 驱动为 1，两层嵌套的子模块必须读到 1"。

**顺带澄清一个曾经的误判**：曾经怀疑"顶层 `accClk` 网是 1 而八位寄存器 `clk` 引脚读到 0"是引脚↔net 的 bug。
用探针在**每个轮次、每个引脚**上核对不变量（`readBit(pin) === 该脚所在 net 的值`）：
真设计全量跑完得到 **0 处真不一致**（唯一"不一致"是 net 尚未赋值 `'Z'`、按既有约定读 0，
见 `gate-netlist.ts` 的 `readBit` 注释）。原来的"1 vs 0"是**跨不同轮次/不同运行比较**造成的错觉。

**为什么零延迟模型必然塌掉**：本关时钟是【运算控制】内部一条**延迟链**（accClk 由门控信号
经多级延迟生成）——**延迟就是功能本身**：它构成一个受控的**环形振荡器**，每次按键振几下，
寄存器靠这些沿写入。零延迟求值把"延迟"当成 0，环路就退化成纯代数方程，
**要么收敛到一个静态电平、要么（奇数级反相）不收敛**；两种都产生不了"沿"。
这不是接线问题，而是**建模缺口**：门级要处理这类电路，就必须有**有界延迟**或**事件驱动推进**。

### 10.3 一个必须记住的坑：timing 口径下的门级读数是**静默回落**，不是门级结论

`judge.ts` 里门级快路限定 `mode === 'logic'`（生产上 `handle.ts` 传的是**玩家当前视图模式**，
所以快路**只在逻辑视图生效**）。拿 `mode:'timing'` 去跑 `judgeDesign(..., { gateSeqSpecs })` 时
**门级根本不会被执行**，会静默回落到元件级。实测（同一进程内交错调用，直跑门级 vs 走 judge）：

```
A 直跑 runGateVectors:        pass=false row1=0x6f     ← 门级真实结论
B judgeDesign(logic, 门级):   pass=false row1=0x6f
D judgeDesign(timing, 门级):  pass=true  row1=0x3f     ← 门级没跑，元件级跑了两遍
```

把门级**强制**放进 timing 口径再测（临时放开开关）：`pass=false`。
**结论：任何"timing 口径下门级与元件级一致 0/67"的读数都是假的**，它量的是
"元件级跑两遍"。第一次排查时正是被这个假读数误导过（曾据此误判为
"元件级逻辑模式定点不唯一"）。**教训**：比较两个引擎时，必须确认门级那一遍真的执行了
（例如断言耗时差异、或临时加日志），否则仪器会给出"完全一致"的假绿。
现在这条已经**自动化**：`apps/studio/test/gate-fast-whitelist-precondition.test.ts`
不信任"看起来一致"，而是逐关逐行核对白名单里的每一关。

**更重要的一课（本条最该被记住的东西）：先怀疑自己的读数，再怀疑引擎。**
这一轮排查里我先后给出过两条**错的**结论，都是**仪器假象**、而不是引擎行为：
① "顶层 accClk 网=1 而八位寄存器 clk 引脚=0" —— 实为**跨不同轮次/不同运行**比较出来的；逐轮逐脚核对后是 **0 处真不一致**；
② "门级组合环 64 轮不收敛、accClk 反复横跳" —— 实为探针打在 `settled = !changed` **赋值之前**，一直打印上一次的值；重测每个向量都 `unstable=false`。
两条都让我差点去"修"一个并不存在的 bug。**规矩**：任何"引擎行为异常"的结论，
在动手改引擎之前必须先能**在同一时刻、用不变量**把它复现出来
（例如"引脚读数必须等于它所在 net 的值"这种一句话能写清的不变量），
并把复现写成**测试**——写不成测试的，很可能只是量法有问题。
主动证伪自己上一轮的读数，比多修一个 bug 更值钱：**假绿/假红不挖出来，后面每次量门级都在自欺。**

  在快路生效口径下门级 `pass=false` / 29 行旧值，按"宁可不快不能算错"继续回落元件级

### 10.5 关卡作者须知：什么关卡吃不到门级快路

**门级快路是"零延迟逻辑仿真"的标准模型** —— 这是早就拍过的建模决定，本节**不改它**，
只把边界说清楚，免得它变成隐形的坑。

#### 什么关卡吃不到（会**自动回落元件级**）

若某关的**时钟 / 控制信号来自延迟链** —— 也就是**延迟本身是功能的一部分**
（典型：s3-calc 的【运算控制】内部多级反相链给寄存器造出建立/写入时序，
按键向量还带 `settlePs: 1_000_000`）—— 那么零延迟求值会把"延迟"当成 0：

- 环路退化成**纯代数方程**，要么收敛到一个**静态电平**、要么（奇数级反相）不收敛；
- **两种都产生不出"沿"**，而这类关卡的寄存器恰恰靠"沿"工作 → 门级读数会**慢一拍/读旧值**。

本关实测就是如此：门级 `accClk` 稳定为静态 0/1（每向量 `unstable=false`），
而元件级时序口径下它是一串**真在跳变的脉冲**（上电窗口 12 次跳变、按 C 再加一个沿）。
结果：门级 67 行里 **29 行**读旧值。

**回落是安全的**：judge 发现门级不适用（或关卡不在白名单）时**静默回落元件级引擎**，
**判定结果仍然正确**（s3-calc 元件级 67/67），代价只是**没有加速**
（本关门级反而比元件级慢 6 倍，所以这里连"亏"都算不上）。

#### 作者自查（三条，改完关卡顺手过一遍）

1. **时钟是不是外部时钟口？** 如果时钟由内部逻辑/延迟链生成，就要预期吃不到快路。
2. **向量是不是靠 `settlePs` 等"建立时间"？** 需要"等一会儿才稳"的关卡，通常就属于延迟即功能。
3. **跑审计**：`npx vitest run apps/studio/test/gate-fast-audit.test.ts`，看你这关在不在"⛔ 回落元件级"里、
   原因是什么。**新增关卡会自动出现在这份清单里**，不用靠人记。

#### 当前清单（审计实测输出，供对照）

```
[门级快路审计] logic 关卡 20 个：能吃到 18 个
  ✅ 已放行 s2-sr-latch / s2-btn-latch / s2-d-latch / s2-dff / s3-half-adder / s3-full-adder /
     s3-adder-4 / s3-adder-8 / s3-alu / s3-bcd2bin / s3-bin2bcd / s3-display / s3-seg-de /
     s3-seg-fg / s3-display2 / s3-reg-8 / s3-encoder / s3-digit-entry

  ⛔ 回落元件级 s3-calc：门级结论与元件级不同（pass true→false，逐行数值差异 58/67）
```

审计还会**自动拦住漏网**：若某关门级明明能算对（pass 与元件级相同、逐行数值 0 差异）却没进
`GATE_FAST_LEVELS`，它会以"该放行却没放行"判红 —— 少赚加速和"静默算错"一样都要被发现。

#### (a) 有界延迟 / 事件驱动推进 —— 记为**未来可选**，本轮不做

若将来确实想让这类关卡也吃到快路，正解是让门级能表达延迟：
**给每个门加有界延迟（如 1 个延迟单位）或改用事件驱动推进**，让延迟链真的振出"沿"。

- 本轮**明确不做**：这是对"门级 = 零延迟逻辑仿真标准模型"这个**既定产品决定**的重新开题，
  为了一个关卡去扩大范围不划算；而且本关的排序是**正确性优先**，而它现在**已经正确**。
- 真要做的话**必须**同时满足：全关卡对照表回归 0 差异（`gate-fast-report.test.ts`）、
  白名单前置条件护栏全绿、`gate-calc-delay-clock.test.ts` 的第二条断言按预期翻红（那是提醒改本节的信号）。

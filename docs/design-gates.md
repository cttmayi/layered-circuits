# 拆分设计：元件 → 门 → 模块

> 目标：把玩法拆成三层，**契约（协约）只钉在最底下的元件层**，让玩家从某一章起
> 完全不用再碰元件，直接用「门」搭复杂模块 —— 计算因此变简单。

## 0. 三层阶梯

```
第 0 层  元件 ──► 基础门       ← 只有这一层受契约约束（元件集 / 成本线 / 延迟线）
第 1 层  门   ──► 组合模块     ← 与契约无关：门已经把契约"吃"进去了（契约在门的内部）
第 2 层  模块 ──► 整机         ← 与契约无关
```

一句话原则：**契约约束的是"用哪些元件、元件多贵多慢"，不是"怎么搭电路"。**
门一旦封装好，它的成本和延迟就把契约的差异吸收掉了，上层不必再关心。

## 2. 顶层菜单：按"层"分章

| 章 | 玩家用什么 | 关卡字段 | 契约菜单 |
|---|---|---|---|
| 第 0 章 · 元件与门 | 只给元件，手搭门 | `moduleAccess: 'none'` | **显示**（可换 rtl / cmos / ttl / dtl） |
| 第 1 章 · 用门搭模块 | 给一组基础门 | `moduleAccess: 'listed'` + `allowedModules` | 隐藏 |
| 第 2 章 · 用模块搭整机 | 给自己的模块（封装玩法） | `moduleAccess: 'all'` | 隐藏 |
| 第 3 章 · 时序 | 同上 + 时钟关 | 同现状 | 隐藏 |

每章开头一句"本章只用什么"，把"契约只作用在元件层"讲成世界观，而不是藏在代码里。

## 3. 关卡内的菜单：左侧面板三个区（第一步要做的改动）

```
┌ 我的元件    可用 2/6        ← ① 受契约约束（复杂关默认收起）
│   三极管 NPN   价格 2
│   基极高电平导通 ···  延迟 1.0 ns
├ 基础门      本关 3 个       ← ② 新建：本关提供的门（teachingModulesFor）
│   与非门       成本 10
│   2 入 / 1 出 ·····  延迟 2.5 ns
├ 我的模块    12 个           ← ③ 现状：自己封装的
│   半加器       成本 60
│   1 入 / 1 出 ·····  延迟 6.5 ns
```

- ① **我的元件**：只有这一区受契约约束。复杂关整区收起 —— 从第 1 章起玩家根本不用看元件。
- ② **基础门**：新增区，内容 = 本关允许的门（`allowedModules` 过滤后的
  `teachingModulesFor(family)`），卡片复用现有模块卡样式（成本 + 延迟 + 入/出），
  拖放或"点击选中 → 点画布"都可用。逻辑版口径下不显示延迟（沿用现有 `mode` 开关）。
- ③ **我的模块**：不变。
- **默认展开策略**：关卡声明默认展开哪一区（如 `openSections: ['gates']`），
  第 1 章进来只展开②、①收起。`useOpenSections` 已存在，加默认值即可。
- **契约菜单**（`FamilyPicker`）：只在第 0 章出现，其余章节隐藏。

## 4. 连带的数值改动（不能漏）

允许用门之后，参考解会比手搭更省 —— 现有的 `budgetHalf` / `optimalHalf` / 延迟预算必须
按**门版参考解**重标，否则成本线和延迟线会失真。

- 参考解：`teachingSolutionOf(levelId, family)` 已支持按契约出解，再加"门版参考解"。
- 成本线 = 门版参考解成本 ×2（沿用现有口径）；延迟预算 = 门版参考解实测延迟 ×2
  （沿用现有口径，见 `levels-ari.ts` 里 52 ns / 76 ns 两处的做法）。
- **门要收钱**（= 其内部元件成本，例如非门 6 元）。不收钱则"成本最优"这条核心玩法失效。
- **判定器零改动**：模块是编译期内联的，成本/延迟照算；逻辑版 / 时序版开关同样适用。

## 5. 一期最小可玩（实施顺序）

1. **菜单分区**：①元件 ②基础门 ③我的模块 + 分区默认展开策略。
2. **注入门**：关卡 `moduleAccess !== 'none'` 时把本关允许的门注入画布库。
3. **一关示范**：「用门搭半加器」（`moduleAccess: 'listed'`，参考解只用门）。
4. **重标该关成本线 + 延迟预算**（先量后改）。
5. 通了再铺第 1 章（8–10 关）与其余章节。

## 6. 已拍定的三个选择

1. **第 1 章先给三个门**：非门 + 与非门 + 或非门；其余门（与门 / 或门 / 异或门）按关卡逐步给。
2. **第 0 章（手搭门）只留 3 关**：非门 / 与非门 / 或非门各一关，别让玩家手搭十个门。

## 9. 逻辑版新引擎：门级求值（7 个门是原子，去掉强弱）

### 9.1 为什么

逻辑版（第 8 关起 20 关的判定口径）此前只是**抹平延迟**，底下仍然把画布上的门展开成
NPN / RES / DIO 求值，而且带着强/弱驱动那一套（强压弱、同强度冲突判 X）。它算的是"真实电路的
电气行为"，在逻辑版里是多余复杂度：`s3-calc` 展开后有 **6191 个元件**，逻辑版判定也要 1.9 s，
手机更扛不住。

### 9.2 模型

- **7 个基础门是原子**（非/与非/或非/与/或/异或/同或）：直接按真值函数算，**不往下钻到元件**。
- **复合模块 = 门之间的连线**（全加器、BCD→二进制…都只是门的组合）。
- **值域 4 个：0 / 1 / X / Z**（Z = 悬空）。**没有强度、没有优先级**：
  同节点多驱动 0 撞 1 → X；无驱动 → Z；不比"谁更强"。
- **Kleene 三值逻辑**：AND 遇 0 即 0（另一输入 X 不影响）、OR 遇 1 即 1。
  这与时序版电路稳定后的结论一致，也是"逻辑版只判逻辑"该有的口径。
- **时序器件**（D 锁存 / DFF / 寄存器）在无延迟下是**代数环**（交叉耦合门），
  必须由调用方用「**状态 + 时钟沿**」模型处理：当前值保持，时钟沿更新。这一层不在门级核心内。
- **适用边界**：只对**纯模块**的设计启用（第 8 关起的 20 关正好全是）；
  自由模式里元件与模块混搭的设计**维持现状**（走元件级逻辑求值），风险最小。
  1~7 关是时序关，逻辑版本就不在那几关生效，元件级语义在时序版里完整保留。

### 9.3 落地进度

- ✅ **第 1 步（已完成）**：`packages/sim-core/src/gate-logic.ts` —— 4 值核心 +
  7 门真值函数 + `mergeDrivers`（多驱动合并，无强弱）+ 多输入折叠 + 输入不足按 X 补齐。
  10 条测试：真值表、Kleene 吸收律、Z→X、多输入、多驱动、4×4 全枚举。
- ⬜ **第 2 步**：按 `Design.nets` 把门连起来求值（拓扑排序 + 迭代到稳定）。
- ⬜ **第 3 步**：时序器件的状态 + 时钟沿模型（锁存器 / DFF / 寄存器）。
- ⬜ **第 4 步**：判定与画布仿真接上这条快路（纯模块设计自动启用，混搭不变）。
- ⬜ **第 5 步**：逻辑版下模块展开只到门（看不到元件层）。
- ⬜ **第 6 步**：实测 speedup（`s3-calc` 判定 21.9 s → 目标毫秒级）+ 守住

## 10. s3-calc 门级/元件级分歧排查记录（2026-10）

目标：让 `s3-calc` 在对照表仪器（`apps/studio/test/gate-fast-report.test.ts`）里变成
「差异 0/N ✅」，通过后才允许进 `GATE_FAST_LEVELS` 白名单。

### 10.1 修好了一个真 bug：一个引脚接多条网名（pin → net 索引只认一条）

**症状**：门级读数与元件级**整片相反**（元件级上电 Q=1，门级读成 0）。

**根因**：`packages/sim-core/src/gate-netlist.ts` 的 `makePinIndex` 原来用
`Map<pinKey, netId>` —— 一个引脚只记住**最后一条** net。但门版参考解里
**同一个引脚挂多条不同网名**是常态，而元件级编译（`flatten.ts`）会把同一引脚上的
各条网名**并成同一个节点**（电气上就是一根线）。于是只有"最后一条 net"拿到驱动，
别的网名永远停在 0：

- 八位寄存器 `q0..q7` ↔ 顶层 `acc0..acc7`（`mod8.q[i]` 同时挂在两条网上）；
- 数字输入寄存器 `q0..q7` ↔ `er0..er7`；
- ALU 的异或/全加器各段、`sumc*` 进位链同理。

最小复现（已写成回归测试 `packages/sim-core/test/gate-pin-alias.test.ts`）：
一条 net 接在 A 门输出上，**同一个引脚**还挂着另一条 net `mid`；修之前 `mid` 永远是 0。

**修复**：`GatePinIndex` 增加 `netsPinTo: Map<pinKey, string[]>`（一个引脚 → 所有 net），
`pinToNet` 保留为首条（兼容旧读法）；驱动推送（`gate-netlist.ts` 与 `gate-seq.ts` 的
3 处 push 循环）改成**写给每条 net**，`readBit` 对多条 net 取 `mergeDrivers` 合并。

**实测（按判定的真实口径 `mode:'timing'` 跑 `judgeDesign`）**：s3-calc 差异
**58/67 → 0/67**，`pass` 两边都是 true。
但注意：**判定实际走的是 `mode:'logic'`**（`judge.ts` 里门级快路只认 `mode === 'logic'`），
所以这条修复本身**不足以**让对照表转绿 —— 见 10.2。

### 10.2 逻辑版（判定真正用的口径）仍有分歧：58/67，卡在 ACC 的时钟上

实测（本机，逐向量逐网对比 + 门级状态槽 dump）：

| 口径 | 元件级 | 门级 | 差异 |
| --- | --- | --- | --- |
| timing（仅参考） | 0x6f / 0x6f …（逐行两边一致） | 同左 | **0/67 ✅** |
| **logic（判定真用）** | 0x6f → 0x3f（row1 清屏后归 0） | 恒 0x6f（一直显示 "99"） | **58/67 ❌** |

- 元件级 logic 模式：row0 `disp=0x6f`，**row1（C 清屏）之后是 `0x3f`（"00"）**，
  与关卡期望一致（`pass=true`）。
- 门级 logic 模式：**一直 `0x6f`**，`pass=false`。
- 定位到的最内层：门级顶层 `运算控制` 的输出网 `accClk=1` 是**对的**，
  但八位寄存器的 `clk` 引脚读数恒为 **0**，于是 ACC 的从锁存器**永远等不到上升沿**
  （状态槽 `mod8/modN/mod3/q#0` 全是 0，`updates` 里没有 ACC 的写入），显示因而一直停在 ER。

**为什么对不上**：门级把时序器件建模成「状态 + 时钟沿」，而元件级 logic 模式是
**无延迟的定点求解**（`Simulator.settle()` 迭代到稳定）：交叉耦合的锁存器在逻辑模式里
是**代数环**，它收敛到的值与元件级 timing 模式**并不一样**（同一份设计，元件级逻辑模式 0x3f /
元件级时序模式 0x6f）。也就是说 `s3-calc` 的 ACC 恒 1 → CTRL 组合环在 64 轮迭代上限内没有稳定
（实测 `settled=false`，回落到"保持上一次的 net"），门级于是停在一个与元件级 logic 不同的不动点。

### 10.3 结论与下一步

- **不放白名单**：s3-calc 判定口径（logic）下差异 58/67，按"宁可不快不能算错"继续回落元件级。
- 已经修的 pin↔net 多网名 bug **保留**（它是真 bug：让门级读数整片相反，且 timing 口径下差异 58→0），
  并加了回归测试。
- 下一步（按性价比排序）：
  1. **先查元件级 logic 模式的定点是否唯一/稳定**：`settle()` 的迭代顺序会让锁存器收敛到
     不同不动点（实测 0x3f 与 0x6f 两个）。若这是"实现细节"，就该给逻辑模式定一条规则
     （例：交叉耦合回路在逻辑模式下一律按**保持上一次的值**处理），而不是让门级去猜。
  2. 再给门级补"未稳定时保持上一次状态"的**逐字节**口径（现在只有 net 级），
     让它在组合环上的行为与元件级逻辑模式对齐。
  3. 顺带：`运算控制` 内部的 accClk 是 10 级反相链，逻辑模式下这条链本身也参与组合环，
     值得单独量一次（是否真的需要 10 级延迟，能不能改成与时钟沿无关的写法）。

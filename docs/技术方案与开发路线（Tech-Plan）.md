## 0. 实施修订记录（M0 落地时对本文的修正）

实施 M0 时发现三处需要修正，均已写进代码与 `docs/sim-semantics.md`：

1. **通路元件传递规则**：原方案只说「强驱动压过弱驱动」，实际会出问题 ——
   若三极管无条件双向传递，浮空节点会通过两个导通三极管互相「自证」一个强电平，
   形成物理上不存在的假稳态（RTL 与非门的中点会永久锁死为 0）。
   修正为：**通路元件只向「外部驱动更弱」的一侧传递电平**（强度取 `min(强侧, 元件上限)`），
   并排除元件自身的贡献。这条规则同时解释了「电阻分压 → X」。
2. **时序分析改用实测法**：原方案的「编译期图论 STA」在开关级模型里会因双向通路产生大量伪环
   （VCC—电阻—输出会把节点合并成团），得出「组合电路被判定为时序电路」「关键路径为 0」等错误结论。
   改为用**同一套时序仿真**逐输入做 0→1 / 1→0 翻转，实测输出最后一次变化时刻。
   好处是与硬核模式完全自洽（面板显示的延迟就是仿真器的延迟），代价是每个输入 2 次仿真（封装时算一次并缓存）。
   整机规模（M4+）可再叠加图论 STA 做增量优化。
3. **电源轨是免费端口**：GDD 的 4 种计费元件里没有电源，但电阻上拉/三极管集电极都需要 VCC/GND。
   定为「免费端口实例」（成本 0，不计入 4 种元件统计）。
4. **参考电路澄清**：GDD 的「非门 = 2 三极管 + 3 电阻」对应
   「共射反相级 + 射极跟随器输出级」；若两个三极管都接反相级，实际是**缓冲器**。
   已用测试固化，避免后续按错误直觉设计关卡。

## 1. 结论速览

**技术栈一句话**：TypeScript 全栈的 Web 应用（Vite + React + 自研 Canvas 渲染层），
仿真内核是零依赖的纯 TS 包，跑在 Web Worker 里，同一份内核在 Node（排行榜校验 / CI）里复用；
桌面端后期用 Tauri 2 打包同一个前端。

**三条架构铁律**（违反任何一条，项目后期都会痛）

1. **仿真/编译内核是纯函数式纯 TS 包，零 DOM、零 React、零引擎依赖。**
   理由：只有同构才能在 Web Worker（不卡 UI）、Node 服务端（排行榜可信校验、防作弊）、CI（回归测试）三处跑同一份确定性代码。
2. **三极管层用「开关级 + strength 语义」仿真，不做 SPICE 模拟。**
   GDD 0.2 已锁定"纯逻辑仿真、无物理模拟"；MNA/牛顿迭代会给玩家"仿真不收敛"这种无法理解的反馈。
3. **封装模块 = 内容寻址的不可变模板（Merkle hash），编译一次、实例化多次。**
   一次性解决：不可逆向修改、版本保留、成本递归 O(1)、黑盒仿真、存档完整性、排行榜防篡改。

**不要选游戏引擎**（Unity / Godot / Phaser / Cocos）：

| 维度 | 游戏引擎 | Web 技术栈（推荐） |
|---|---|---|
| 本作 90% 的工作量（原理图 CAD、面板 UI、波形图、数据表格） | 引擎弱项，UI 系统难用 | 强项，React + CSS 直接做 |
| 服务端校验 / 排行榜（复用同一份仿真） | 做不到，需两套实现 | 同构 TS，同一份代码 |
| 玩家存档/关卡 JSON、可分享链接、SEO/网页版试玩 | 麻烦 | 天然 |
| 大规模拖拽式 CAD 交互手感 | 一般 | 完全可控 |
| 后期上 Steam / 桌面 | 好 | Tauri 2 打包同一前端（体积 ~10MB） |

结论：引擎能带来的只有"动画特效"，而这类硬核设计游戏不需要。**Web 优先，桌面后置。**

## 2. 核心技术难点与解法

### 2.1 难点一：三极管/电阻/二极管到底怎么仿真？

GDD 2.1.1 把 NPN 三极管、电阻、二极管、电容定为唯一成本根节点，玩家要"用 2 三极管 + 3 电阻搭非门"。
这里有三种实现选择：

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 模拟电路仿真（MNA + Newton-Raphson / SPICE） | 物理真实 | ❌ 收敛失败、性能差、无法给出"逻辑错误"人话提示，违背 GDD 0.2 |
| B. **开关级仿真 + 强度语义（推荐）** | 数字抽象：三极管=受控开关，电阻=弱驱动，二极管=单向开关 | ✅ 快、确定、错误可解释，Logisim / Digital 走的这条路 |
| C. 直接给门级原语（AND/OR/NOT） | 那玩家就不是"从三极管搭门"了 | ❌ 违背核心卖点 |

**方案 B 的具体语义（必须写成规范文档 + 单元测试，M0 阶段就锁死）**

节点值 4 值：`0 / 1 / X（冲突、未知）/ Z（高阻悬浮）`
驱动强度 3 级：`STRONG（三极管导通、外部输入）/ WEAK（电阻上拉/下拉）/ Z（无驱动）`

元件模型：

- **NPN 三极管**：3 端（B/C/E），`B = 1` → C-E 导通（STRONG 驱动），`B = 0` → 断开（Z）。延迟 1ns。
- **电阻**：WEAK 驱动（把节点拉向所连的另一端），延迟 0.5ns。
- **二极管**：3 端语义（A/K），A 电位高于 K 且非 Z 时导通为可导通的 STRONG（简化为单向开关），延迟 0.8ns。
- **电容**：见 2.2 的时钟建模说明，**不参与开关级求值**。

节点归约规则（resolution）：

```
有 STRONG 驱动 → 取该值；多个 STRONG 且值冲突 → X，并报「驱动冲突/短路」错误
无 STRONG、有 WEAK → 取 WEAK 值（可被任意 STRONG 覆盖）
全部为 Z → Z；新手模式下按 0 处理并给出「引脚浮空」警告
```

这套规则的价值：玩家所有的错误都能被翻译成人话 —— 输入浮空、上下管同时导通短路、输出悬空、多驱动冲突、
反馈环振荡。这是"教学型硬核游戏"的体验基础。

> 可选增强（非必需）：编译期做**子网模式识别**（"2 三极管 + 电阻 = 反相器"），
> 用于成本提示、参考解对比、教学高亮；但**正确性绝不依赖模式识别**。

### 2.2 难点二：双模式时序仿真（一套内核，两套语义）

GDD 2.3 要求"新手科普模式（忽略延迟）"和"硬核工程模式（含延迟/建立保持/竞争冒险）"。

- **统一内核：离散事件仿真（DES, Discrete Event Simulation）。**
  事件队列（二叉堆 + 时间轮分桶），事件 = `(时间, 节点, 值, 强度)`。元件被激活即计算、产生新事件。
- **新手模式**：把所有传播延迟设为 0，退化为**固定点迭代收敛（settle）**：
  反复求值直到无变化；超过 `max(100, 2 × 节点数)` 轮仍未稳定 → 判定「组合环/振荡」。
  时序违例不检查，X 一律降级为"不确定但放行"。
- **硬核模式**：恢复 1/0.5/0.8ns 延迟，节点采用**惯性延迟（inertial）**决定"有效值"，
  同时保留毛刺事件用于波形显示与冒险检测；在 DFF/锁存器模板上声明 `setup / hold / clock-to-q`，
  仿真时检查数据与时钟沿的到达时间 → 输出「建立时间违例 @ t=12.3ns」。
- **静态时序分析（STA）**：编译期在模块模板上计算最长/最短路径延迟，得到引脚到引脚的**延迟矩阵**。
  这块信息一石三鸟：① 硬核模式下模块黑盒仿真仍能算时序（GDD 6.2 要求）② 右侧面板显示"当前电路最高可用时钟频率"
  ③ 把 GDD 里"低成本电路延迟不均"的博弈点变成可视化数据。

**时钟来源（GDD 未定义，必须补）**：建议把时钟作为**关卡提供的免费输入端口**（不算元件成本），
而玩家用"电容 + 元件"搭出的振荡环，由编译器识别后折叠为 clock primitive，周期由 RC 参数推导（宏观模型）。
❌ 不要真跑模拟振荡 —— 语义和性能都会崩。

### 2.3 难点三：模块封装、黑盒仿真、成本递归（性能生死线）

GDD 6.2 的"仿真黑盒、成本递归只在结算时"是关键性能设计，工程上要落成两级编译：

```
原理图（玩家编辑）
  → 网表 Netlist（连通性 + 引脚绑定）
  → 模板编译 Compile（每个模块封装修剪一次）
       · 拓扑排序后的扁平指令表（SoA 数组，非对象图）
       · 端口延迟矩阵（STA 结果）
       · unitCounts = {npn, res, dio, cap}（成本，O(1) 查表）
       · 纯组合模块若输入位宽 ≤ 12 位 → 折叠为真值表/BDD 快速路径
  → 实例执行 Simulate（三级模块不展开，只做引脚绑定 + 事件驱动激活）
```

两个必须做对的地方：

1. **绝不递归展开整机。** 256×8 RAM ≈ 16384 个 D 触发器 ≈ 10 万个三极管，flatten 一次就废了。
   正确做法是"模板编译一次 + 实例化多次"，模板甚至可 AOT 编译成 JS 函数（`new Function`）或 WASM。
2. **成本不做运行期递归。** `unitCounts` 在封装时就累加好（子模块计数 + 自身元件数），
   成本 = 点积（`2·npn + 1·res + 1.5·dio + 3·cap`）。GDD 2.2 的"递归"发生在**封装那一刻**，
   结算/实时预览/溯源树全部是查表 —— 递归语义不变，复杂度从 O(元件数^深度) 降到 O(1)。

**内容寻址**：`moduleHash = H(自身元件 + 引脚定义 + 各子模块的 moduleHash 有序列表)`。
收益：同版本自动去重、同名不同内容区分、**"禁止逆向修改"变成数据结构层面的天然性质**（改了 hash 就变了，是另一个模块）、
存档/排行榜可校验。同功能多版本（标准/极简/高稳定）天然支持。

### 2.4 难点四：编辑器（无限画布 + 布线 + 撤销重做）

- **渲染**：自研 Canvas2D 渲染层（视口裁剪 + 脏节点重绘 + 层级回收），抽象出 `Renderer` 接口。
  理由：因为模块被黑盒化，**单屏图元数量天然有界**（玩家一个模块内通常 < 500 个元件），Canvas2D 完全够用。
  若后期要特效/上万图元，再换 [PixiJS v8](https://pixijs.com/blog/8.16.0)（WebGL/WebGPU 批渲染）——接口已隔离，替换成本低。
  备选：Konva（上手快、性能上限低）。
- **布线**：正交（曼哈顿）折线 + 交叉点自动加 junction dot；交互期用橡皮筋预览；
  自动布线用网格 A*（带障碍避让），可选 WASM 的 libavoid。MVP 允许手工画拐点，自动布线后置。
- **撤销重做**：命令模式（Command + Inverse），撤销栈只存逆操作（省内存），
  文档模型不可变（Zustand + Immer 或自研 patch）。**视图状态（缩放/选中）不进撤销栈、不进存档。**
- **状态管理**：Zustand（轻、无 Provider 地狱）。文档 store / 视图 store / 仿真 store 三者分离。
- **总线（GDD 缺失但必需）**：阶段 3 的 8 位寄存器、加法器、ALU 若没有位宽概念，
  玩家要手工连 8 根线 × N 次，体验崩塌。**建议 M0 就把 wire 定义为带 `width` 的 bundle**，
  引脚声明位宽，一位宽的总线在画布上画成一条粗线并标 `[7:0]`。
  这是整个 GDD 里最容易被低估、但改动成本随开发线性上升的设计缺口。

### 2.5 难点五：确定性与防作弊

- 仿真必须**确定性**：禁止浮点参与逻辑判定（延迟用整数皮秒/飞秒）、事件同刻排序用稳定 tie-break（实例 id）。
- 排行榜/最低成本记录的校验在服务端跑同一份 `sim-core`：上传"网表 + 模块库（含 hash）+ 激励"→ 服务端重放 → 验证功能与成本。
  这一步决定了排行榜的可信度，也是"铁律 1"的最大回报。

| 后端（后置） | Fastify + Postgres + Drizzle（复用 sim-core） | 排行榜校验、云存档 | — |
| 桌面 | Tauri 2（[v2 已稳定](https://v2.tauri.app/release/core/)） | 复用同一前端，包体小 | 需 Node 原生能力才考虑 Electron |
| 测试 | Vitest + fast-check（属性测试）+ Playwright（E2E） | 仿真器必须靠黄金测试 + 属性测试守 | — |
| 质量 | Biome（lint+format）、tsc --noEmit、GitHub Actions | 一条命令 `pnpm check` | — |
| 校验 | Zod（schema + 迁移链） | 存档/关卡/网表全量校验 | — |
| 内容工具 | Python + z3 / OR-Tools CP-SAT（离线求最优解算预算） | 数值平衡不能拍脑袋 | — |
| 错误/埋点 | Sentry + PostHog | 关卡通过率/卡点分析 | — |

## 5. 数据模型草案

```ts
// packages/schema —— 只列关键字段，实际用 Zod 定义并生成类型
type Unit = 'npn' | 'res' | 'dio' | 'cap';
type UnitCounts = Record<Unit, number>;            // 成本载体，L1 基础元件才有

interface BaseComponent {                          // 4 种基础元件之一
  kind: 'base';
  unit: Unit;
  pins: Pin[];
  params?: Record<string, number>;                 // 如电阻阻值（仅用于时钟推导）
}

interface ModuleTemplate {                         // 玩家封装出来的模块（不可变）
  hash: string;                                    // Merkle 内容哈希 = 身份
  name: string; version: string; kind: 'logic'|'seq'|'mem'|'cpu';
  ports: { name: string; dir: 'in'|'out'; width: number }[];
  body: Netlist;                                   // 内部原理图（黑盒时仍可在溯源里展开）
  costs: UnitCounts;                               // ★封装时算好，成本 = dot(costs, 单价)
  delays: Record<string, Record<string, number>>;  // ★引脚→引脚最长延迟（STA）
  isSequential: boolean;
}

interface Level {
  id: string; stage: 1|2|3|4|5|6; type: 'main'|'cost'|'timing'|'retro';
  allowedUnits: Unit[];                            // 可用素材（GDD 3 的阶段约束）
  allowedModules?: string[];                       // 复古复用关：只允许早期版本 hash
  budget: number;                                  // = optimalCost × 1.15~1.20（由求解器算出）
  optimalCost: number;                             // 求解器产出，CI 校验
  vectors: TestVector[];                           // 激励序列
  assertions: Assertion[];                         // 真值表断言 / 波形时序断言
  clock?: { freqHz: number; required?: boolean };  // 硬核模式强制高频时钟
  referenceSolution?: Netlist;                     // 官方参考解，CI 保证关卡可通关
}
```

结算判定：`功能全部断言通过 && 成本 ≤ budget`；得分 = `1 - 成本/预算` 归一化（GDD 2.2.3）。

## 6. 关卡与数值平衡工具链（最容易被忽视，但决定内容质量）

1. **预算由求解器产出，不靠拍脑袋。**
   `tools/opt-solver`：输入"目标布尔函数 + 可用元件/模块库 + 优化目标=最小底层成本"，
   用 z3 / OR-Tools CP-SAT 求最小成本实现（小规模 ≤ 4 输入可直接穷举；
   目标为门级网表时用 SAT 编码最小化门数，再用各门的三极管实现成本加权）。
   产出 `optimalCost` → 关卡预算自动生成 → 数值可回归、可调参。
2. **每个关卡必须带官方参考解**，CI 跑：参考解功能通过且成本 ≤ 预算。
   这道护栏保证引擎一改，关卡不会悄悄变成"不可通关"。
3. **关卡判定用"目标真值表 + 时序断言"，不用文字描述**。
   自动生成全部输入组合（或声明 don't-care），断言客观、可穷举、易写测试。
4. **关卡编辑器要早做**（M3 之前）。6 阶段主线几十个关卡，手写 JSON 必崩。

## 7.6 M1 交付记录（阶段 1 关卡闭环）

**可玩循环**：`apps/studio` 默认进入关卡模式 → 第 1 关「非门」→ 左侧「本关目标」卡片给出目标真值表
与预算进度 → 搭电路 → 点「校验本关」→ 右侧逐行对比 + 错误原因 → 通过后「通关并封装为【非门】」
→ 模块进入**全局组件库**（跨关卡持久化）→ 解锁下一关。

| 关卡 | 功能 | 最优成本（参考解） | 预算 | 硬核时序预算 | 素材约束 |
|---|---|---|---|---|---|
| 非门 | 反相 | 4（单管共射，输出弱 1） | 5 | 2.5ns | 只能手搭 |
| 与门 | a·b | 4（二极管与） | 5 | 2.0ns | 只能手搭 |
| 或门 | a+b | 4（二极管或） | 5 | 2.0ns | 只能手搭 |
| 与非门 | ¬(a·b) | 7（2 三极管串联下拉） | 8.5 | 3.5ns | 可用组件库 |
| 或非门 | ¬(a+b) | 8（二极管或 + 单管反相） | 10 | 4.0ns | 可用组件库 |
| 异或门 | a⊕b | 28（4 个与非门） | 34 | 7.0ns | 可用组件库 |
| 同或门 | ¬(a⊕b) | 32（异或 + 反相） | 38.5 | 9.0ns | 可用组件库 |

- **判定规则**（`@lc/compiler` 的 `judgeDesign`）：功能逐向量比对 + 成本 ≤ 预算 + 结构检查（逻辑门关卡
  若被判定为时序电路直接不通过）；硬核工程模式再加「关键路径 ≤ 关卡时序预算」。
- **关卡可通关性由 CI 保证**：`packages/content` 的测试对每关参考解跑一遍判定，断言「零错误、通过、
  成本 == optimalHalf、满分、硬核时序达标」；另有用例验证「封装与非门 → 4 个模块拼异或门」的跨关卡复用。
- **关卡数据即规格**：`vectors`（真值表）+ 端口名（a/b/y）+ `allowedUnits`（阶段 1 不给电容）+ 预算/最优，
  全部写在 `packages/content/src/levels.ts`，判定与 UI 都从同一份数据派生，改关卡不用改代码。
- **存档**：进度（通关记录 / 最好成绩 / 尝试次数）与组件库存 `lc-studio-progress-v1`；
  每个关卡的画布草稿单独存 `lc-studio-level-<id>-v1`，自由模式草稿存 `lc-studio-doc-v1`。

**已知取舍**：`optimalHalf` 目前取「参考解成本」而非求解器搜出的真最优（M3 的 `tools/opt-solver` 接手）。
成本 ≤ 最优即满分，所以偏宽松的最优值只会让满分更容易，不会出现「无解关卡」。异或/同或的参考解是
手搭展开版（固定成本、CI 无需组件库），玩家用自己封装的与非门拼出来成本相同。

## 9. GDD 未定义、但必须提前锁定的设计缺口

这些不是技术问题，而是**决定技术实现的语义决策**，晚定会推翻已完成的内容：

1. **总线/位宽**：给 wire 加 `width`，引脚声明位宽。（最紧急，影响阶段 3 全部关卡）
2. **时钟从哪来**：建议关卡提供免费时钟端口；电容振荡折叠为 clock primitive，周期由 RC 推导。
3. **浮空输入 / 短路 / 组合环**在新手模式下算不算错？建议：浮空 → 警告不判错；短路 → 判错；组合环 → 警告 + 输出 X。
4. **扇出限制**：真实 RTL 有扇出问题，GDD 未提。建议不引入（或仅在硬核模式作为可选严格档），否则难度爆炸。
5. **二极管能否直接搭门（DTL）**：若能，会绕开"三极管是唯一开关"，但成本策略更丰富。建议允许，因为"低成本极简方案"正是核心乐趣。
6. **引脚是否允许同名/多驱动**：需明确"多驱动 = 错误"还是"线或/线与"。建议新手模式报错。
7. **关卡判定粒度**：真值表全覆盖 vs 逐时刻波形断言，需在关卡 DSL 里都支持（阶段 2 之后必须用波形断言）。
8. **黑盒如何携带时序**：GDD 6.2 的"黑盒不逐元件仿真"与硬核模式时序检查有冲突，解法就是 2.2/2.3 的引脚延迟矩阵（STA 预计算）。
